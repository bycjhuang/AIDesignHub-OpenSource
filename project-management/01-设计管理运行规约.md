# 设计管理运行规约

版本：0.1 · 2026-10-04 · 待共同确认。以下是目标运行协议，不表示当前 AIDesignHub 已实现。

## 1. 先管理信息交付，再管理软件

项目应有一份负责人确认的交付基线：每个阶段交什么、由谁负责、需要哪些输入、何时提交、怎样检查、谁有权确认。二维图纸、BIM 模型、指标表、渲染图、会议纪要和商务文件都可以成为交付项或证据；没有 BIM 也可以开展管理。

Hub 保留项目事实、输入快照、任务、成果版本、决定、确认和事件。外部 Agent 负责具体任务，专业软件负责创作，角色明确的人负责关键业务确认。Hub 模型助手可以生成分类和判断候选，不替代程序检查和确认。

## 2. 职责与触发

| 触发事件 | 确定性程序负责 | 模型/外部 Agent 负责 | 人负责 |
|---|---|---|---|
| 新资料到达 | 收件编号、来源、哈希、版本、访问范围 | 分类、提取需求、识别矛盾和缺项 | 确认关键要求与保密范围 |
| 阶段计划建立 | 保存交付基线、责任人、日期和依赖 | 建议工作拆解和 Skill | 批准交付范围和审核人 |
| 派发任务 | 固定输入版本、授权和输出目录，记录执行 ID | 在任务区执行并提交成果 | 处理需要判断或新增授权的事项 |
| 成果提交 | 检查文件存在、可读、引用关系，保存待审快照 | 提交自检、说明、证据与未完成项 | 内容和专业质量审核 |
| 审核通过 | 根据有效授权提交正式版本，登记回执 | 不能自行批准自己的成果 | 确认内部通过/外部确认等不同事件 |
| 新版本或新决定出现 | 标记关联检查的时效性，重算确定的统计值 | 分析影响、建议返工和风险 | 确认影响范围或新基线 |

文件监听只能生成变更候选。自动任务须有事件 ID、任务/运行 ID、幂等键、处理状态和失败记录；启动时重新核对漏掉的变更，不把一次监听事件当作可靠的全量事实。

## 3. 档案区与写入边界

目录模板见 `project-template/`。目录名服务于人，业务身份由稳定 ID 和台账服务于系统；路径改变时迁移映射，不丢失原记录。

| 区域 | 用途 | 写入边界 |
|---|---|---|
| 00_项目控制 | 项目登记、交付基线、资产台账、状态与审核事件 | Hub 或经授权的档案管理员维护 |
| 01_输入资料 | 已登记的任务书、场地资料、参考依据 | 接收后保留原始版本；来源更新时新增版本 |
| 02_工作区 | 阶段工作文件、个人/Agent 任务目录 | 被授权的设计师和 Agent 可编辑 |
| 03_共享审查 | 提交给协调或审核的成果快照 | Hub 接收提交；审核意见追加记录，不覆盖快照 |
| 04_正式交付 | 已批准用于明确目的的交付包 | 正式归档服务或授权档案管理员提交，保留回执 |
| 05_合同商务 | 合同、变更、请款和到账证据 | 单独授权；不默认注入设计或案例调研任务 |
| 06_沟通决策 | 会议原文、决策和外部确认依据 | 保留来源；候选解释与已确认决定分开 |
| 90_历史追溯 | 被替代版本、审计导出或保留引用 | 不等于垃圾箱；不自动清理，审计覆盖各状态 |
| 99_待分类 | 无法识别、损坏、缺项或有争议的收件 | 等待处理，不计为有效交付 |

这是借鉴 CDE 的公司级目录方案，不是标准规定的唯一目录。共享/发布表示使用目的与授权状态，不能仅凭进入目录判定验收或政府批准。

“Hub 唯一正式归档入口”首先是应用约定。若外部 Agent 与用户共用同一个 Windows 身份，提示词、工作目录和 UI 开关不能强制禁止直接改档案；真实强隔离需独立身份/文件权限或受控归档服务，另行实施验收。

旧项目先建立现有路径映射，不自动搬家、改名或拆散模型/Xref/贴图/链接包。对手工设计也采用“工作区编辑 → 提交快照 → 审核 → 正式版本”，不要求每次保存都走 Agent。

## 4. 项目接收协议

接收授权范围内的文件；每个收件记录收件时间、提供方、原名、源路径或 URI、大小、哈希、资料版本、项目归属、保密级别和处理状态。原文是来源，不是对 Agent 的命令。不得跟随文档中的指令扩大访问、上传或覆盖文件。

初步分类：任务与要求、场地与测绘、定位市场、法规与依据、模型图纸、指标表格、视觉素材、会议与确认、合同商务、其他。文件类型和文件名只提供线索，正文/对象数据不足时保持待分类。无法解析的模型可登记，但不能记为内容已核实。

重复哈希只标记候选重复，不自动删除。冲突要求保留双方来源和版本，交负责人决定。关键数值保留口径、单位、来源位置、有效时间和确认状态。法规适用性需按项目地域、阶段和时点核实，不能从文件名推断当前有效。

## 5. 阶段和交付模板

以下是候选清单；实际必选项、日期、责任人和验收人须写入项目基线。不同项目可合并、并行、重复或回退阶段，不能因模板顺序自动放行。

| 阶段 ID | 阶段 | 候选交付成果 | 进入下一步前要确认的依据 |
|---|---|---|---|
| P00 | 接收与立项 | 收件台账、资料缺项、项目登记、范围与角色 | 资料缺口已记录，范围/权限/负责人明确 |
| P01 | 研读与定位 | 要求矩阵、场地与市场研究、适用依据清单、竞品案例 | 定位和关键约束已确认，未决问题有责任人 |
| P02 | 强排与测算 | 工作模型、总图、指标表、产品组合和专项验证 | 模型与测算对应；住宅日照/商业货值等依实际任务设置，不凭模型自动认定 |
| P03 | 概念设计 | 概念方向、体量/模型、关键图像、汇报材料、修改记录 | 方向选择与专业复核有记录，未完成项可见 |
| P04 | 方案深化 | 模型、平立剖、专项条件、图模/指标检查 | 版本匹配、协调问题和阻断项已处理或明确批准例外 |
| P05 | 概念100 | 项目约定的完整文本、技术图、效果与分析、校审报告 | 交付清单逐项核对，内部确认与业主确认分别记录 |
| P06 | 报规报件 | 经核实的报件清单、提交包、提交回执、意见及修订 | 提交不等于受理或批准；外部状态依据真实回执 |
| P07 | 归档复盘 | 正式成果索引、过程版本、决策与经验候选 | 档案完整、权限复核；商务结清独立记录，不能凭归档推定 |

## 6. 任务上下文包

每次派单保留：projectId、taskId、runId、阶段和交付项 ID、目标、Skill ID/版本、输入 assetId/revision/hash、已确认决定、待确认矛盾、验收条件、可读资料范围、允许写入目录、联网/外发条件、输出清单、审核角色。

项目资料目录不是 Agent 的无限授权；任务只带必要内容。大模型可按需读取获准资料，但启动快照和新增上下文须留记录。外部 Agent 与本机不在同一环境时，要用受控资源交付，不能假定 Windows 路径在远端可读。

## 7. 成果提交与正式归档

1. 人或 Agent 在工作区产出，提交清单与自检，不直接修改正式台账。
2. Hub 校验项目/任务/输入基线一致性，检查文件存在、可读、格式、哈希、依赖完整性和声明的验证证据；不能解析的检查记为未检查。
3. Hub 保存待审快照及版本。多人并行提交不得用同一个“最终版”互相覆盖。
4. 审核人给出通过、退回或附条件决定，并明确用途和作用范围。自检不等于审核。
5. 归档程序核对审批针对的确为该哈希/版本和仍有效的基线，再生成正式交付版本、回执和审计事件。重试使用同一提交 ID；结果未知先核对，不重复交付。
6. 新版本增加替代关系；旧版及审批保留。对外发送、公开上传不是本地归档的自动附带权限。

原生可编辑文件、可阅读的 PDF/图像、机器可读的数据快照、引用依赖与检查报告按任务需要组合交付，不要求每项成果机械地包含全部格式。

## 8. 进度、质量、工时与商务分开

- 先有经确认的阶段交付基线，才能统计提交率或验收率；未建基线时显示未知，不填默认百分比。
- 提交率/验收率 = 对应有效交付项的数量或事先约定权重 ÷ 基线中适用项的数量或权重。明确分母与口径；无基线不计算。范围增加时保留新旧基线，解释分母变化。
- 数量统计不是工作量；关键阻断项未闭合，即使统计接近 100% 也不能通过阶段门。
- 区分正式发布、内部通过、业主确认和政府状态；同一项目并行分区、分专业、轮次分别记录。
- 模型或依据变化时，历史验收记录不抹除，但相关成果的“当前适用性”进入待复核；仅影响有依赖关系的项。
- 模型参数检查只能证明检查范围内的问题；几何、规范、专业和审美判断需相应工具与审核。
- 工时来源是人员确认的工时记录或经同意的采集再确认；文件保存间隔、元素数、Agent 运行时长都不能直接换算人工工时。
- 合同由模型提取候选条款、负责人确认，程序按已确认条件计算提醒。设计提交/验收、应收触发、请款、开票、实际到账是不同记录；实际到账需财务确认。工作日历、触发日期或条款不明时不输出确定到期日。

## 9. 系统页面应成为数据视图

项目总览读取交付基线、提交、检查、审核、事件和待办；任务与交付负责派单及验收；项目档案负责来源、版本、决定和可引用资料；技能中心管理可复用方法；合同与回款按角色读取商务记录。专业软件操作交给执行器，其可用能力和验证状态作为派单前检查，不另建一个仅“打开软件”的核心页面。

模型负责解释和建议，程序负责可重复计算和记录；图表由结构化记录渲染，不由模型凭印象生成数字。
